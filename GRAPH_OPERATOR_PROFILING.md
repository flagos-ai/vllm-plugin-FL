# Runtime Kernel Profiling

This workflow records the rank-0 GPU activity generated by one fixed vLLM
graph-mode workload. It does not profile CUDA Graph construction.

The workload contains 64 concurrent requests. Each request has exactly 4096
input tokens and 1024 output tokens. A complete warmup batch finishes before
`/start_profile`; only the second complete batch is inside the profiling
window.

## DeepSeek-V4-Flash

Terminal A:

```bash
bash tools/graph_operator_profile/serve_deepseek_v4_flash.sh
```

Terminal B, after the server is ready:

```bash
bash tools/graph_operator_profile/profile_request.sh \
  deepseek_v4_flash \
  tools/graph_operator_profile/deepseek_v4_flash_request.json
```

Results:

```text
/vllm-workspace/graph_operator_profile_runs/deepseek_v4_flash/results/
```

## Output files

`kernel_summary.json` is the physical kernel inventory. Its top-level key is
the kernel name. Each value contains a `summary` and an `events` dictionary.
An event key has this form:

```text
rank0:trace_000:gpu_000000123
```

The trace index and GPU-event index make the key unique within one extraction.
Every rank-0 runtime kernel event is stored under exactly one kernel name.

Each event contains its duration, timestamp, process, thread, device, stream,
External id, and logical metadata when a unique runtime CPU operator match is
available. Missing metadata is represented by JSON `null`; the event is never
discarded.

`mapping_status` is one of:

- `operator_shape_matched`
- `operator_matched_shape_missing`
- `operator_matched_dtype_missing`
- `operator_matched_metadata_missing`
- `shape_ambiguous`
- `operator_ambiguous`
- `missing_external_id`
- `no_cpu_op_match`

Each kernel summary contains `total_time_us`, `profiling_time_ratio`,
`profiling_time_pct`, and `total_call_count`. The ratio and percentage use the
sum of all rank-0 runtime kernel durations as the denominator. This is GPU
activity time, not request wall time. Concurrent kernels can overlap.

`operator_index.json` contains every runtime `cpu_op` emitted for rank 0. Its
top-level key is the operator name. Shape/dtype variants and CPU call counts
come only from the runtime trace. `kernel_names` is a reverse index; kernel
duration is not copied into this file, so it must not be added to the physical
kernel totals.

`non_kernel_gpu_activity.json` retains rank-0 `gpu_memcpy` and `gpu_memset`
events. They are separate because they are GPU activities but not kernels.

`summary.json` records scope, counts, durations, mapping coverage, and
conservation checks. A valid extraction requires all three conservation booleans
to be `true`:

- `kernel_event_count_matches`
- `kernel_time_matches`
- `kernel_mapping_time_matches`

## Collection boundary

The server scripts explicitly use:

```bash
export VLLM_FL_ENABLE_GRAPH_CAPTURE_PROFILE=0
unset VLLM_FL_GRAPH_CAPTURE_PROFILE_DIR
```

`VLLM_FL_ENABLE_GRAPH_CAPTURE_PROFILE` defaults to disabled. Enabling it
requires a true value and `VLLM_FL_GRAPH_CAPTURE_PROFILE_DIR`, but capture data
is intentionally outside this workflow and is never read by the extractor.

The upstream `/start_profile` and `/stop_profile` behavior is unchanged and
still writes one raw trace per rank. The extractor selects rank 0:

```bash
python3 tools/graph_operator_profile/extract_operator_shapes.py \
  --runtime <runtime_trace_directory> \
  --rank 0 \
  --output-dir <result_directory>
```

The launch scripts use graph mode, `max_num_seqs=64`, and CUDA Graph capture
sizes `[1,2,4,8,16,32,64]`. Prefix caching is disabled. DeepSeek uses the
standard CUDA Graph path through `VLLM_USE_BREAKABLE_CUDAGRAPH=0`.

## Completeness boundary

The inventory is complete for kernel, memcpy, and memset events emitted in the
selected rank-0 runtime trace. It does not claim all-rank coverage.

CUDA Graph replay exposes physical kernels but usually does not replay the
original PyTorch CPU operators. A graph-internal kernel may therefore have no
recoverable operator, input shape, or dtype in the runtime trace. Such an event
remains in `kernel_summary.json` with null logical fields and an explicit
mapping status.

CPU-only operators remain in `operator_index.json`. Operators visible only
during CUDA Graph construction are intentionally excluded. Fused kernels may
represent multiple logical operators and are not assigned by kernel-name
guessing.

Different requests, batch sizes, sequence lengths, sampling settings, TP
ranks, or MoE routing can activate different kernels and shapes. Rank 0 is a
reproducible single-rank view, not proof that another rank has no additional
activity.
